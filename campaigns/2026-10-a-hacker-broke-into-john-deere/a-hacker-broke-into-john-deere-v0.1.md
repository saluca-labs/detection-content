# AI Agents Breach 100+ Websites via Cairn Platform: A Detection Engineering Analysis of Autonomous AI-Driven Intrusions

## Abstract

In October 2026, The Verge reported that a hacker breached more than 100 websites using an army of AI agents that mostly operated on their own, according to findings from the AI security firm Norforge. Reuters reporting indicated that victims included John Deere, SharkNinja, and Cummins, with attacks spanning companies based in the US, Canada, Australia, and Japan. The attacks were orchestrated through Cairn, an open-source AI platform that describes itself as a "general-purpose problem-solving engine." Norforge uncovered the activity through exposed work on more than 20 Cairn instances deemed "likely malicious." The most active attacker laid out "preferred intrusion tactics" using fewer than 100 Chinese characters, with successful breaches taking about 23 hours. This working paper examines what detection opportunities exist for defenders given the limited information available from this secondary news source. Two Sigma rules are proposed, one targeting outbound connections to the Cairn platform and another targeting sustained web application probing over an extended period. The paper is explicit about what cannot be detected from this source and acknowledges significant limitations in building detection logic from news coverage rather than forensic analysis.

## Detection opportunities

Given the severe constraints of this source, the detection opportunities available are limited and largely inferential. Two Sigma rules are proposed, each tied to a specific observation that can be extrapolated from the source text, though neither can be validated against the actual technical characteristics of the attacks described.

The first detection opportunity relates to the Cairn platform itself. The source establishes that the attacks were orchestrated through Cairn, an open-source AI platform. If an organisation's internal users were to adopt Cairn for legitimate purposes, or if a compromised account were to use it internally, outbound connections to Cairn infrastructure would be visible from the corporate network. The rule `01-outbound-connection-to-cairn-ai-platform.yml` targets this scenario by alerting on outbound connections to the Cairn AI platform from corporate networks.

However, the source is explicit that the attacks described were external. The hacker used Cairn to attack target websites from outside. The source does not describe any scenario in which Cairn was used from within a victim's network. Therefore, this detection rule addresses a hypothetical internal misuse scenario rather than the actual attack chain described in the source. It is included because the emergence of a new AI platform with demonstrated offensive capability warrants monitoring for internal adoption, but defenders should understand that this rule would not have detected the attacks as they occurred.

The rule would need to reference known Cairn infrastructure, such as domains or IP ranges associated with the platform. The source does not provide any such indicators. Building the rule would require independent research into Cairn's public infrastructure, which goes beyond the facts in the source text. The source does note that Cairn is an open-source platform, which suggests that its code repository and any associated documentation might reveal infrastructure details, but the source itself does not enumerate them.

The second detection opportunity relates to the duration of the attacks. The source states that successful breaches took about 23 hours, according to Reuters. This figure implies sustained automated activity against target websites over an extended period. If an attacker is probing a web application for vulnerabilities over nearly a full day, that activity should produce a pattern of requests that stands apart from normal user traffic. The rule `02-sustained-web-application-probing-over-extended-pe.yml` targets this pattern by hunting for unusual automated reconnaissance or probing against web-facing assets spanning approximately 23 hours.

This rule maps to MITRE ATT&CK technique T1595, Active Scanning. The logic would look for a sustained pattern of requests from a single source, or a coordinated set of sources, targeting web endpoints over a period approaching 24 hours. The source does not describe what the probing looked like at the network level. It does not specify request rates, endpoint paths, HTTP methods, response codes, or any other technical characteristics of the activity. The rule must therefore be built on general principles of what sustained automated web probing looks like, rather than on the specific behaviour of the Cairn agents.

The 23-hour figure is significant because it suggests the AI agents operated continuously or near-continuously over that period. Human attackers typically work in bursts, with idle time between actions. Automated tools can operate continuously, but most scanning tools complete their work in minutes or hours rather than spanning a full day. A 23-hour campaign suggests a methodical, iterative approach that might not trigger rate-based alerts but would be visible as a persistent low-and-slow pattern in web access logs. Defenders with access to web application firewall logs, reverse proxy logs, or web server access logs could hunt for source IP addresses that maintained activity across a 24-hour window with patterns consistent with automated probing.

The rule could be structured to look for a single source IP address making requests to a web application over a sustained period, with characteristics such as a high ratio of error responses, requests to a diverse set of endpoints, or patterns consistent with vulnerability scanning. However, without knowing the actual behaviour of the Cairn agents, any specific thresholds or patterns would be speculative.

It is worth noting that the source describes the AI agents as having "mostly operated on their own" and carrying out attacks "with little involvement from the human hacker." This autonomy suggests the agents may have exhibited more consistent and predictable behaviour than a human attacker, potentially making the sustained probing pattern more recognisable. However, this is an inference from the source's language, not a technical observation.

Both rules are constrained by the same fundamental problem: the source provides no technical detail about how the AI agents operated. Any detection logic built from this source is necessarily built on inference and general principles, not on observed attacker behaviour. The rules should be treated as starting points for further development once the underlying Norforge research becomes available, not as production-ready detections.

No logs, network captures, endpoint telemetry, or system images were examined in the preparation of this paper.
